# Full agent reporting + a `defineWatcher` plugin API

Two connected upgrades to how Pragma sees agents:

1. **Rich reporting.** Today an agent report is a single coarse status
   (`running` / `attention` / `done` / `cleared`). Grow it into a stream of the agent's
   **full message** — assistant text, tool calls, files touched, and a flag that
   **sub-agents are active** — so a client that is not the terminal (mobile, another
   client) can read what the agent is doing and approve from afar.
2. **`defineWatcher`.** A new, separately-defined plugin function. When a plugin's agent
   launches, Pragma assigns it a **host-side watcher** (if one is defined) that can read
   the terminal output as a **stream** and **emulate key presses**. This is the
   groundwork layer for out-of-terminal / mobile interaction — not the mobile UI itself.

<Card className="my-4">
  <CardHeader>
    <CardTitle>At a glance</CardTitle>
    <CardDescription>What ships, and the decisions behind it</CardDescription>
  </CardHeader>
<CardContent className="text-sm space-y-2">

- **Messages are a new frame, not a fatter status.** Status stays exactly as-is (it drives
  the dot). A new `AgentMessage` frame carries the rich, append-only turn content on a
  parallel channel. Old clients keep working; new clients subscribe to the extra stream.
- **Message source = both.** Each host-tool plugin emits **structured** messages from its
  transcript when it can (Claude Code already parses one); a **watcher** can scrape the
  terminal stream as a fallback where no structured source exists. _(Your call.)_
- **Sub-agents = a boolean, not a tree.** `subAgentsActive` (a count) on the message.
  We show that sub-agents are running; their contents are out of scope for now. _(Your call.)_
- **Watchers run host-side in a Bun sidecar.** A new `pragma-watch` sidecar (modeled on
  `pragma-ai` / `pragma-github`) hosts `defineWatcher` functions with full `@pragma/sdk`
  access, so a watcher survives the UI closing and can stream + inject for the agent's
  whole life. _(Your call.)_
- **All plumbing already exists.** `GET /v1/sessions/{id}/events` (NDJSON output stream)
  and `POST /v1/sessions/{id}/input` (write bytes) are live in `pragma-gateway` and wrapped
  by `@pragma/sdk`. The watcher runtime is a consumer of these, not new transport.
- **One source of truth.** The message schema lands in `@pragma/constants`
  (`schema.json`) so TS and Rust generate from the same definition — same rule the current
  `AgentReportPayload` follows.

</CardContent>
</Card>

## Part 1 — Full message reporting

The rich content rides a **new, parallel channel**. We do not widen the status enum or bloat
`AgentReportPayload`: status is small, frequent, and drives the dot; a message is larger,
append-only, and only some clients want it.

<TabsContent value="schema">

New `@pragma/constants` definitions (regenerate TS + Rust with `bun run generate`):

- **`AgentMessage`** — one append-only entry in an agent's turn:
  - `agent`, `worktreeId`, `tabId` — routing keys, same as `AgentReportPayload`.
  - `id` — stable id for the message (so re-sends dedupe / updates replace).
  - `role` — `assistant` | `tool` | `user` | `system`.
  - `text?` — the assistant/user text for this entry.
  - `toolCalls?` — array of `{ id, name, status: running|done|error, summary? }`.
  - `files?` — array of `{ path, change: read|edited|created|deleted }`.
  - `subAgentsActive` — integer count of running sub-agents (**flag only**, no contents).
  - `ts` — emit time.
- **`AgentMessageKind`** — enum used by the frame tag.

Design rules that keep it honest:

- **Append-only + upsert by `id`.** Streaming a tool call from `running` → `done` re-sends
  the same `id`; consumers replace. No partial-diff protocol.
- **Optional everything but routing + `id` + `ts`.** A plugin that only knows text emits
  text; one that parses a transcript fills `toolCalls`/`files`. Matches the "both sources"
  decision.
- **No secrets by construction.** Message text is whatever the host tool already prints;
  we do not add file _contents_, only paths + change kind.

</TabsContent>

<TabsContent value="transport">

Mirror the existing status path one-for-one, on its own frame so nothing about the current
status flow changes:

- **Protocol** (`crates/pragma-protocol/src/lib.rs`): add `RequestKind::AgentMessage`
  (payload = JSON `AgentMessage`) and `EventFrame::AgentMessage { ... }`. The server fans it
  out to agent subscribers exactly like `EventFrame::Agent`.
- **Server** (`crates/pragma-server`): route the new request kind to the same subscriber
  broadcast used for agent status. Messages are **not** persisted server-side in this phase
  (the dot store already treats status as ephemeral); a bounded per-tab ring buffer for
  replay is noted as a follow-up.
- **App bridge** (`agent_events.rs`): match `EventFrame::AgentMessage`, emit a new
  `pragma:agent-message` Tauri event.
- **Gateway** (`crates/pragma-gateway/src/routes/agents.rs`): expose the message stream over
  HTTP (extend the agents subscription NDJSON) so `@pragma/sdk` — and later a mobile client —
  can read it without the Unix socket.

</TabsContent>

<TabsContent value="cli">

**CLI.** New subcommand alongside `agent report`:

```sh
pragma-cli agent message --agent <id> --json '<AgentMessage JSON>'
# or read the JSON payload from stdin for large messages:
some-transcript-parser | pragma-cli agent message --agent <id> --stdin
```

It reuses the exact connect-write-exit path `agent report` already uses (`direct.rs`), just
writing an `AgentMessage` frame instead of `AgentReport`.

**Plugin API.** Two additions, both additive (minor version bump):

- **Emit side** — extend the plugin runtime with a typed emitter so a plugin's own code /
  watcher can push a message without shelling out:
  `bridge.agents.reportMessage(msg: AgentMessage)`. Under the hood this is the same as the
  CLI call. (`@pragma/sdk` gets `reportMessage()` next to `reportStarted`/`reportStopped` in
  `agents-client.ts`.)
- **Read side** — a new hook `useAgentMessages(worktreeId, tabId?)` in
  `packages/plugin/src/hooks.ts` (delegating onto `__PRAGMA__.hooks`), returning the live
  message list for a tab. Extend `PluginAgentStatusEntry` consumers rather than replacing
  them: status and messages stay separate hooks.

</TabsContent>

## Part 2 — `defineWatcher`

A watcher is defined **separately** from `defineAgent` (your requirement) and **bound by
agent id**. When Pragma launches an agent that has a registered watcher, the host spins up a
watcher instance for that session inside the `pragma-watch` sidecar.

<Card className="my-4">
  <CardHeader>
    <CardTitle>The contract</CardTitle>
    <CardDescription>`packages/plugin/src/watcher.ts` — a new file, exported from `index.ts`</CardDescription>
  </CardHeader>
<CardContent className="text-sm">

```ts
/** Declares a watcher a plugin attaches to one of its agents' sessions. */
export interface WatcherDefinition<TConfig = unknown> {
  /** The `defineAgent` id this watcher attaches to. */
  agent: string;
  /** Runs once per launched session; lives until the session exits. */
  watch: (ctx: WatcherContext<TConfig>) => void | Promise<void>;
}

export interface WatcherContext<TConfig> {
  sdk: PragmaClient; // full gateway SDK
  config: TConfig; // this plugin's validated config
  session: { id: string; tabId: string; worktreeId: string };
  /** Async iterator over decoded terminal output for this session. */
  output: AsyncIterable<string>;
  /** Emulate key presses / paste text into the session. */
  sendKeys: (data: string) => Promise<void>;
  /** Push a rich message onto the Part 1 channel (scrape fallback source). */
  reportMessage: (msg: Omit<AgentMessage, "agent" | "tabId" | "worktreeId">) => Promise<void>;
  /** Resolves when the session exits; also an AbortSignal for cleanup. */
  signal: AbortSignal;
}

/** Declares a watcher contribution. Author defines this as a separate function. */
export function defineWatcher<TConfig = unknown>(
  input: WatcherDefinition<TConfig>,
): WatcherDefinition<TConfig> {
  return input;
}
```

</CardContent>
</Card>

<Alert className="my-4">
  <AlertTitle>`sendKeys` writes real bytes into a live terminal — treat it as privileged</AlertTitle>
  <AlertDescription>

A watcher that emulates key presses can approve prompts and run commands on the user's behalf.
The plan gates it: watchers only attach to **their own plugin's** agents, run in the sandboxed
sidecar with no ambient filesystem/network beyond the SDK, and every `sendKeys` is logged to
the daemon log with the originating plugin + watcher id for audit. Auto-approval policy (what a
watcher is _allowed_ to answer) is deferred to the mobile-consumer plan, not decided here.

  </AlertDescription>
</Alert>

<TabsContent value="runtime">

**Where it runs — `pragma-watch` sidecar.** A new Bun-compiled sidecar, added to
`externalBin` in `tauri.conf.json` next to `pragma-ai` / `pragma-github`, staged by the same
`stage-daemon-sidecar.sh` mechanism.

**Lifecycle:**

1. App launches an agent (existing flow in `src-tauri/src/agents.rs`).
2. If a plugin registered a `defineWatcher` for that agent id, the app tells `pragma-watch`
   to start a watcher instance, passing `{ pluginId, agentId, sessionId, tabId, worktreeId }`
   and the gateway socket path.
3. The sidecar loads the plugin's watcher bundle, builds a `WatcherContext`, and calls
   `watch(ctx)`.
4. When the session exits (`EventFrame::Exit` / stream close), `signal` aborts; the sidecar
   tears the instance down. A max-lifetime backstop mirrors the existing hook-watcher guard.

Running host-side (not in the React webview) is what makes it survive the UI closing — the
requirement for mobile/remote approval later.

</TabsContent>

<TabsContent value="io">

Both directions already have transport — the watcher is a **client of the gateway**, no new
Rust I/O primitives:

- **Read stream:** `output` wraps `GET /v1/sessions/{id}/events` (the NDJSON stream from
  `attach_stream`, `sessions.rs:73`), already exposed by `@pragma/sdk` streaming. The sidecar
  decodes output frames into an `AsyncIterable<string>`.
- **Emulate keys:** `sendKeys` wraps `POST /v1/sessions/{id}/input` (`sessions.rs:94`, which
  calls `registry.write`). Bracketed-paste / control sequences are the caller's responsibility,
  same bytes the terminal would send.

So `defineWatcher` is a thin, well-typed ergonomic layer over transport that already ships.

</TabsContent>

<TabsContent value="reg">

`definePlugin` gains an optional `watchers` contribution, parallel to `agents`:

```ts
definePlugin({
  // ...
  agents: [claudeAgent],
  watchers: [claudeWatcher], // new
});
```

- `packages/plugin/src/plugin.ts` — add `watchers?: WatcherDefinition[]` to
  `PluginUiContributions` (or a new `PluginRuntimeContributions`), export types.
- `apps/pragma/src/plugins/PluginProvider.tsx` — collect registered watchers, index by agent
  id, and on agent launch dispatch to `pragma-watch`.
- Host-side registry in `apps/pragma/src-tauri/src/plugins.rs` learns which agent ids have
  watchers so it can start one at launch.

Per the repo rule, this is generic plugin-runtime infrastructure (allowed in
`packages/plugin` + `apps/pragma/src/plugins` + `plugins.rs`), **not** per-tool core code.

</TabsContent>

<TabsContent value="example">

A minimal watcher that scrapes output into the Part 1 message channel and auto-dismisses a
known benign prompt:

```ts
export const claudeWatcher = defineWatcher({
  agent: "claude-code",
  async watch({ output, sendKeys, reportMessage, signal }) {
    for await (const chunk of output) {
      if (signal.aborted) return;

      // Scrape fallback: turn visible tool lines into messages.
      const tool = chunk.match(/^\s*[⏺●]\s+(\w+)\((.*)\)/m);
      if (tool) {
        await reportMessage({
          id: crypto.randomUUID(),
          role: "tool",
          toolCalls: [
            { id: crypto.randomUUID(), name: tool[1], status: "running", summary: tool[2] },
          ],
          subAgentsActive: /Task\(/.test(chunk) ? 1 : 0,
          ts: Date.now(),
        });
      }

      // Emulate a key press to answer a trusted prompt.
      if (chunk.includes("Continue? (y/n)")) await sendKeys("y\r");
    }
  },
});
```

</TabsContent>

## Part 3 — Migrate the existing plugins

Each host-tool plugin keeps its current `agent report` calls (the dot is unchanged) and
**adds** message emission. Where a structured transcript exists we parse it; otherwise the
plugin's watcher scrapes. This is the "both sources" decision applied per plugin.
