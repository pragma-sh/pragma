# Remote Server Re-architecture

Turn Pragma from a single-machine desktop app into a **host server + thin clients** system.
A persistent **`pragma-server`** runs on the machine that holds the repos; clients reach it
**over SSH** (no new auth or TLS layer). The PTY and agent-status model that already exists
in `pragma-daemon` is the template — most of the work is making everything _else_ (git, fs,
db, kanban, GitHub, AI) work the way the daemon already does.

<Card className="my-4">
  <CardHeader>
    <CardTitle>At a glance</CardTitle>
    <CardDescription>What ships and what it costs</CardDescription>
  </CardHeader>
  <CardContent className="text-sm space-y-2">

- **`pragma-daemon` becomes `pragma-server`** — persistent, owns PTYs + all business logic, listens on a `0600` Unix socket (unchanged transport surface). **No TCP port** — the socket file perms are the access control.
- **New `pragma-core` crate** — git/fs/db/kanban/worktrees/projects/agent-registry/fs-watcher extracted out of `apps/pragma/src-tauri` as pure library logic.
- **SSH transport, client-side only — fully wired in Phase 4, no frontend yet.** Phases 1–3 ship the client/server flip over the local socket; Phase 4 then **fully implements** the SSH path end-to-end — the client embeds `russh` and forwards the remote `daemon.sock` via `channel_open_direct_streamlocal` (streamlocal — the Unix-socket analog of `ssh -L`, no TCP port), with a bootstrap `exec` to ensure the server runs. It's exercised via the router DB / CLI / tests; the **frontend host-management UI is deferred** to a later, UI-only phase. **The server never knows SSH exists.**
- **Predictive echo** — client renders printable chars + space locally, gated on a new server `EchoMode` event so password prompts never leak.
- **Server-authoritative state** — snapshot-then-delta subscriptions (the agent-registry pattern, generalized) keep multiple devices in sync; writes serialized server-side with optimistic versioning.
- **Bun sidecars for the JS bits** — `pragma-github` (Octokit) and the existing `pragma-ai` (pi SDK), spawned + piped + proxied by the server. Token/creds stay on the host.
- **Per-project SQLite on the host** (in the project's `.pragma/`) + a small **client-local router DB** mapping project → host. SQLite stays (WAL + pool); **not** Turso.
- **Sync server, quarantined-async client** — server keeps the thread-per-connection model; async lives only in the client's SSH bridge (Tauri already runs tokio).

## Target architecture

The host runs one persistent server; native clients (laptop, phone, second machine) each hold
an SSH connection and subscribe to cheap state streams, attaching a terminal's output **only**
for tabs the user is actually looking at.

```
        ┌──────────────────────────── host machine ────────────────────────────┐
        │  sshd ──(authenticates as you)                                        │
        │   │                                                                    │
        │   ▼  forwarded daemon.sock (0600)                                      │
        │  pragma-server  (was pragma-daemon — persistent)                       │
        │   • PTY sessions + 10k scrollback        (session.rs — unchanged)      │
        │   • agent registry, daemon-wide          (registry.rs — generalized)   │
        │   • pragma-core: git · fs · db · kanban · worktrees · projects         │
        │   • fs-watcher (notify) → change events                               │
        │   • spawns Bun sidecars: pragma-github · pragma-ai (stdio)             │
        │   • per-project SQLite in <project>/.pragma/  (WAL + pool)             │
        └───────────────────────────────────────────────────────────────────────┘
              ▲ SSH (russh) channels, one per stream — codec unchanged
   ┌──────────┼───────────┬───────────────────────┐
   │          │           │                        │
 laptop     phone     2nd machine        (each: 1 agent-status sub +
 (Tauri)   (Tauri)     (Tauri)            1 state sub + N attached terminals)
```

The server is the **single serialization point** and stays fully synchronous — the proven
`pragma-daemon` model carries over untouched:

- Thread-per-connection + `mpsc` fan-out (today's `main.rs` / `session.rs`).
- `rusqlite` sync, behind a small pool; writes serialized (one user, low write volume).
- `notify` fs-watcher consumed on a thread → broadcasts `WorktreeChanged` / `FileChanged`.
- Bun sidecars via `std::process::Command` + reader threads (like the PTY reader threads).

It only ever sees forwarded Unix-socket connections, so **SSH is invisible to it**.

  </TabsContent>

  <TabsContent value="client">

The client needs async because `russh` is async — but Tauri already runs a tokio runtime, and
the async surface is confined to one module:

- A **local socket bridge**: listens on a local Unix socket; per inbound connection it opens a
  `channel_open_direct_streamlocal` to the remote `daemon.sock` and runs
  `tokio::io::copy_bidirectional`.
- The existing client frame code in `pty.rs` keeps doing **synchronous** `UnixStream::connect(...)`,
  pointed at the local bridge socket instead of the daemon.

This is exactly how `ssh -L` works (a local socket fronts the tunnel), so current client I/O
barely changes.

  </TabsContent>

  <TabsContent value="protocol">

Grow the wire protocol from "PTY + agents" into a general **RPC + event bus**, keeping the
length-prefixed codec and the raw-binary PTY fast path:

- **RPC methods** for git / fs / db / kanban / worktrees / projects (request → response).
- **Subscriptions** that send a **snapshot then deltas** — exactly what `subscribe_agents`
  (`registry.rs:183`) already does. Reuse for `WorktreeChanged`, `KanbanChanged`,
  `TabsChanged`, `FileChanged`, plus the new `EchoMode`.
- All method names / payloads / errors defined once in `@pragma/constants` (schema → TS + Rust).

</TabsContent>

## Predictive echo

Two pieces. The novel safety part is that **the server tells the client when echo is on**, so
predictions never appear over a hidden password field.

<Card className="my-4">
  <CardContent className="text-sm space-y-2 pt-6">

- **Server detects echo state.** The PTY slave's termios `ECHO` flag clears when a program reads
  a password (`read -s`, sudo, etc.). The server watches the slave termios (raw fd + `nix::sys::termios`;
  `portable_pty` doesn't expose it) and emits `EchoMode { sessionId, echo: bool }`.
- **Client predicts conservatively.** On a **printable char or space**, when echo is on and the
  cursor is at end-of-line, render it immediately (dim) and reconcile when real bytes arrive.
  **Arrows / tab / enter / ctrl / any escape sequence → stop predicting** until the next confirmed
  state. No cursor-movement prediction. Predictions are per-client local overlays — no cross-device
  coordination.

</CardContent>
</Card>

<Alert>
  <AlertTitle>Why echo gating matters</AlertTitle>
  <AlertDescription>
    Predictive echo masks SSH latency, but it must never speculatively paint a character the program
    intends to hide. Gating every prediction on <code>echo == true</code> is the mechanism that
    keeps password and secret prompts safe.
  </AlertDescription>
</Alert>

  <AccordionItem value="conn">
    <AccordionTrigger>Connection management: background worktrees & tabs cost almost nothing</AccordionTrigger>
    <AccordionContent>

The key move is decoupling **PTY lifecycle** (server-owned, always running) from **agent status**
(one cheap global subscription) from **terminal output + xterm rendering** (lazy, per visible tab).

A client holds, over its one SSH connection:

- 1 channel — daemon-wide agent-status subscription (long-lived, tiny).
- 1 channel — tabs/state subscription (snapshot + deltas; this renders the tab strip without touching any terminal).
- 1 event channel **per visible terminal** (usually just the focused one).
- the pooled request channel + input-writer channel for the active terminal.

Background tabs hold **no** event channel → the server sends them no output → no bandwidth, no
xterm instance. Switching to a tab attaches it and replays scrollback (tmux-style). Disconnect →
all channels close, subscribers pruned, **PTYs keep running**; on reconnect the agent snapshot shows
current state of every worktree and the visible terminal replays scrollback.

**The one cost that does _not_ decouple:** server-side scrollback is allocated **per running PTY**,
not per attached tab. With ~50 open terminals the client still renders only the 1–2 you're looking at,
but the host holds ~50 full rings — so the aggregate-scrollback bound is a _server_ concern handled in
Phase 5, independent of how many tabs are visible. See _Risks & watch-items → Scrollback bound_.

    </AccordionContent>

## Transport over SSH

<Tabs defaultValue="chosen">
  <TabsList>
    <TabsTrigger value="chosen">A — chosen</TabsTrigger>
    <TabsTrigger value="fallback">B — fallback</TabsTrigger>
  </TabsList>

  <TabsContent value="chosen">

**Socket forward + bootstrap exec.** The client opens one SSH `Handle`; each of today's
`UnixStream::connect(daemon.sock)` calls becomes one `channel_open_direct_streamlocal(".../daemon.sock")`
— a 1:1 mapping, frame codec unchanged, independent per-channel flow control preserved. A one-shot
`channel_open_session` + exec runs `pragma-server ensure` to cold-start the server.

- **Server changes:** none — it sees Unix connections.
- **No TCP port:** the socket itself is what's forwarded (streamlocal), so the `0600` perms stay the access control end-to-end. We do **not** add a TCP listener or a transport abstraction.
- **Latency:** best — independent channels, so an output flood can't head-of-line-block keystrokes.
- **Verified:** `russh::client::Handle::channel_open_direct_streamlocal(socket_path)` exists.

**The connect seam (one decision point):** look up the project's host in the router DB →
_local_ host → `UnixStream::connect(daemon.sock)`; _remote_ host → get-or-open the shared SSH
`Handle` for that host and `channel_open_direct_streamlocal(daemon.sock)`. Everything above the
seam (frame codec, `pty.rs`, RPC calls) is identical for both. Phases 1–3 implement only the
local branch; Phase 4 fully implements the remote branch (backend only — no host-management UI)
with no changes above the seam.

</TabsContent>

  <TabsContent value="fallback">

**stdio over exec.** `ssh host pragma-connect` pipes a shim's stdin/stdout to `daemon.sock`. Plain
exec channels always work (zero russh risk) and the shim auto-starts the daemon — but it costs a
process-per-stream or a protocol-level mux, and risks keystroke stalls if single-streamed. Keep as
the fallback only if the `direct-streamlocal` path ever fails.

  </TabsContent>
</Tabs>

## 7-phase rollout

Phases 1–3 are a refactor with **no new user-facing surface** and are independently valuable — they
flip the architecture on a single machine and de-risk everything after.

<Accordion type="single" collapsible className="my-4">
  <AccordionItem value="p1">
    <AccordionTrigger>1 · Extract <code>pragma-core</code></AccordionTrigger>
    <AccordionContent>

Move logic out of `src-tauri` into the new library crate; Tauri commands become thin wrappers
calling `pragma-core` in-process. Behavior-identical, fully testable. **No protocol or UX change.**

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p2">
    <AccordionTrigger>2 · Generalize the protocol</AccordionTrigger>
    <AccordionContent>

Add RPC + event variants to `pragma-protocol`, schema in `@pragma/constants`. Rename
`pragma-daemon` → `pragma-server`; it serves `pragma-core` over the **existing Unix socket**
alongside PTY. Bump `daemon.protocolVersion`.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p3">
    <AccordionTrigger>3 · Route Tauri commands through the socket</AccordionTrigger>
    <AccordionContent>

Extend the client (`pty.rs` → `pragma-client`) so git/fs/db calls go over the socket too. The app
is now a client of the server **even locally** (still one machine). Architecture flipped.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p4">
    <AccordionTrigger>4 · SSH transport + bootstrap</AccordionTrigger>
    <AccordionContent>

Fully wire the `russh` client bridge (`channel_open_direct_streamlocal` + bootstrap `exec`), the
client-local router DB, protocol-version negotiation, and conditional provisioning — the complete
remote path, end-to-end (this also satisfies the "spike `direct-streamlocal` early" risk item). A
second machine can connect, but **only via the router DB / CLI / tests** — the frontend gets **no
host-management UI yet** (adding / selecting / authenticating remote hosts is a later, UI-only
phase). The app's UX stays local-only even though the transport is fully capable.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p5">
    <AccordionTrigger>5 · Per-project DB + fs-watcher + change events</AccordionTrigger>
    <AccordionContent>

Move the workspace schema into per-project SQLite on the host (WAL + pool, in `<project>/.pragma/`).
Add the `notify` watcher and broadcast change events. Multi-device sync emerges; clients become
caches with optimistic versioned writes. Make the server persistent (drop empty-idle exit).

**Bound aggregate scrollback here, too.** Once the server is persistent and may hold ~50 running
PTYs, the per-session 10k ring becomes a real resident footprint (~250–500 MB). Switch the per-session
ring to a **byte budget**, add a **daemon-wide cap / LRU**, and **hibernate idle, unattached sessions**
to disk (rehydrated at the existing attach-time `frames()` replay). See _Risks & watch-items → Scrollback bound_.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p6">
    <AccordionTrigger>6 · Predictive echo</AccordionTrigger>
    <AccordionContent>

Server-side `EchoMode` detection (termios `ECHO`) + event; client-side prediction overlay
(printable + space, gated on echo, reconciled against real output).

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="p7">
    <AccordionTrigger>7 · GitHub + AI sidecars</AccordionTrigger>
    <AccordionContent>

Build `pragma-github` (Bun + Octokit); reparent `pragma-ai` to the server. Server spawns, pipes,
and proxies both; creds stay on host.

    </AccordionContent>

  </AccordionItem>
</Accordion>

Windows is **out of scope for v1**, but the Unix-socket choice does not paint us into a corner —
because the most common Windows dev setup is WSL2, which is a real Linux kernel.

## Risks & watch-items

<Card className="my-4">
  <CardContent className="text-sm space-y-2 pt-6">

- **Editor/diff latency over the network** — the terminal has predictive echo; the editor needs its
  own snappiness (caching + watcher-driven invalidation + chunked/streamed diffs).
- **Path/command injection** — git/fs RPC must validate every path against known worktrees on the host.
- **Server provisioning** — getting a protocol-matched `pragma-server` onto the host (manual install
  for v1; auto-provision later, VS Code-style).
- **Scrollback bound — load-bearing at scale, not a later knob.** A real session count is **up to
  ~50 concurrent PTYs** (many worktrees × projects × agents), and each `Session` allocates its full
  `Scrollback::new(10_000)` ring **at creation, regardless of attach** (`session.rs`) — backgrounded,
  unattached, idle sessions still hold the whole buffer for the persistent server's entire uptime.
  Aggregate ≈ `sessions × ≤10k frames × avg-frame-bytes`: ~50 × 10k × 500 B ≈ **250 MB**, and ~500 MB
  for chatty build/test agents (≈1 KB/frame). Not catastrophic, but enough that the bound must be
  **designed into Phase 5**, not deferred:
  - **Bound by bytes, not frame count** — `SCROLLBACK_LIMIT = 10_000` frames is a poor memory proxy
    when a frame ranges from a keystroke to a screenful.
  - **Global cap / LRU across sessions**, not only the per-session ring — per-session bounding can't
    stop 50 simultaneously-full buffers; a daemon-wide budget evicts/hibernates the coldest.
  - **Hibernate idle, unattached sessions** — with ~50 open but 1–2 attached, the cold majority can
    spill scrollback to disk and rehydrate at the existing `frames()` replay seam on attach.
  - **Cheap structural win:** confirm whether each `EventFrame::Output` still carries its own
    `session_id` inside the already-per-session ring — if so, storing raw bytes and reattaching the id
    only at replay drops 10k redundant string allocs per session.
  - **Note:** this is the one cost that does **not** decouple with attach (see Connection management) —
    client bandwidth/xterm scale with _visible_ tabs, but server scrollback scales with _running_ PTYs.
- **`russh` `direct-streamlocal`** — verified present; Phase 4 now wires it end-to-end (not just a
  spike), which de-risks it directly. B (stdio-over-exec) remains the fallback if it ever fails.

</CardContent>
</Card>
