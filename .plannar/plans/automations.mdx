# Automations

A per-project (and global) automation system. Users drop a **single self-contained
`.ts`/`.js` file** into `.pragma/automations` (project, read across all worktrees) or
`~/.pragma/automations` (global). Each file calls **`defineAutomation`** with a name,
description, a **trigger** (`cron` or `event`), and the automation body. Files are
**esbuild-bundled** (bare imports auto-installed on demand) and executed by a new
**long-lived `pragma-automations` Bun sidecar owned by `pragma-server`** — so automations
run on the host **even when the desktop app is closed**.

A new **full-view Automations screen** (clock icon in the sidebar titlebar) lists
automations grouped **Global / Local**, opens each as an editable **CodeMirror** tab, and
gates newly-detected **local** automations behind a **security approval dialog**.

<Card className="my-4">
  <CardHeader>
    <CardTitle>At a glance</CardTitle>
    <CardDescription>What ships, and the decisions that scope it</CardDescription>
  </CardHeader>
  <CardContent className="text-sm space-y-2">

- **New `@pragma/automations` package** — the runtime the author imports: `defineAutomation` + types, plus the sidecar `src/cli.ts` (NDJSON), compiled to a `pragma-automations` binary like `pragma-ai` / `pragma-github`.
- **`pragma-server` owns the runner** — a new module in `crates/pragma-server` adds (a) a **cron scheduler thread**, (b) an **automations-directory watcher**, and (c) a **managed long-lived sidecar child**. The sidecar transpiles + runs; the server schedules and supervises.
- **Server-side trust store (new)** — the server has no DB today. Add a small server-owned SQLite/JSON store in the server data dir for automation **trust state** (approved / rejected / pending) plus the **content hash at time of verdict**, readable while the app is closed. `rusqlite` is already a workspace dep.
- **App registers project roots with the server** — the server has no project registry; only the app's `pragma.db` knows a project's `.pragma` root + worktree set. On connect the app pushes roots (and known automations) so the server can watch/enumerate and keep crons alive after the app quits.
- **Trust model** — **local** (`.pragma/automations`) automations are **inert until approved** via the install dialog; **global** (`~/.pragma/automations`) are **trusted automatically**. Reject keeps the code on disk and marks it rejected in the store against the file's current content hash — editing the file afterward changes the hash, clears the rejection, and re-prompts on next scan.
- **Events are free-form background listeners** — an `event` automation ships arbitrary listener code that runs in the sidecar background and flips `eventTriggered` to fire the body. Maximum flexibility (this is exactly why local files need approval).
- **npm via on-demand install** — esbuild bundles the file; bare imports are auto-installed into a managed cache, no per-dir `package.json` required.
- **Full-view UI** — clock icon toggles a whole-view mode (Kanban is the precedent), grouped Global/Local sidebar with a worktree subtree for automations unique to a worktree, CodeMirror editor tabs, and an approval dialog.

</CardContent>
</Card>

## The `defineAutomation` API

One default export per file. The author imports from the bundled runtime; the sidecar provides
`ctx` (structured logger, worktree/project paths, a `@pragma/sdk` client for host ops).

<Tabs defaultValue="cron">
  <TabsList>
    <TabsTrigger value="cron">cron trigger</TabsTrigger>
    <TabsTrigger value="event">event trigger</TabsTrigger>
    <TabsTrigger value="types">types</TabsTrigger>
  </TabsList>

  <TabsContent value="cron">

Runs on a schedule. The server's scheduler fires it; the body runs in the sidecar.

```ts
import { defineAutomation } from "@pragma/automations";
import { Octokit } from "@octokit/rest"; // bare import → auto-installed on demand

export default defineAutomation({
  name: "Nightly stale-branch report",
  description: "Every night, list branches with no commits in 30 days and log a summary.",
  trigger: { type: "cron", schedule: "0 3 * * *" }, // standard 5-field cron
  async run(ctx) {
    const stale = await ctx.git.staleBranches({ days: 30 });
    ctx.log.info(`found ${stale.length} stale branches`, { branches: stale });
  },
});
```

  </TabsContent>

  <TabsContent value="event">

The `listen` function is **free-form** and runs in the sidecar background. Call `fire()` (the
`eventTriggered` signal) to run `run`. Anything goes — timers, fs watches, polling an API,
subscribing to a stream — which is exactly why local automations require approval.

```ts
import { defineAutomation } from "@pragma/automations";

export default defineAutomation({
  name: "Alert on build output",
  description: "Watch dist/ and run whenever a new bundle larger than 5MB appears.",
  trigger: {
    type: "event",
    // free-form background listener; `fire` is the eventTriggered signal
    listen(ctx, fire) {
      const timer = setInterval(async () => {
        const big = await ctx.fs.find("dist", { minBytes: 5_000_000 });
        if (big.length > 0) fire({ files: big }); // → eventTriggered: true
      }, 10_000);
      return () => clearInterval(timer); // disposer on unload
    },
  },
  async run(ctx, payload) {
    ctx.log.warn("large bundle detected", payload);
  },
});
```

  </TabsContent>

  <TabsContent value="types">

```ts
export interface AutomationContext {
  log: { info(msg: string, data?: unknown): void; warn(...): void; error(...): void };
  paths: { project: string; worktree: string; global: boolean };
  git: GitClient; // subset of @pragma/sdk
  fs: FsClient; // confined to the automation's root
  // exec/network available but flagged in the approval dialog
}

type Trigger =
  | { type: "cron"; schedule: string } // 5-field cron, host timezone
  | {
      type: "event";
      listen: (ctx: AutomationContext, fire: (payload?: unknown) => void) => (() => void) | void;
    };

export function defineAutomation(def: {
  name: string;
  description: string;
  trigger: Trigger;
  run: (ctx: AutomationContext, payload?: unknown) => void | Promise<void>;
}): AutomationDefinition;
```

  </TabsContent>
</Tabs>

<Accordion type="single" collapsible className="my-4">
  <AccordionItem value="loading">
    <AccordionTrigger>How a file becomes a running automation</AccordionTrigger>
    <AccordionContent>

1. Server dir-watcher sees a new/changed file → computes an automation **id** (stable, path-derived) + content hash.
2. **Trust check** (server store): global root → trusted; local root → look up id. Unknown local id → mark **pending**, broadcast `automationPending`, **do not load**. Known local id with verdict **rejected** → compare stored hash to the current one; mismatch means the file changed since rejection, so treat it like unknown (mark **pending**, broadcast, do not load) rather than staying rejected.
3. On load (trusted/approved): server hands the file path to the sidecar over NDJSON. Sidecar **esbuild-bundles** it (auto-installing bare imports into the managed cache), imports the bundle, validates the `defineAutomation` shape, and **registers** it: cron jobs go to the scheduler; event `listen` runs immediately in the background.
4. Runtime failures (bundle error, throw, bad shape) → sidecar emits a `status: error` line → surfaced in the UI, automation marked errored (not silently dropped).

</AccordionContent>
  </AccordionItem>
  <AccordionItem value="npm">
    <AccordionTrigger>On-demand npm install</AccordionTrigger>
    <AccordionContent>

The sidecar scans bare specifiers, resolves any missing into a **managed cache dir** (server data
dir, shared across automations) via `bun install`/`bun add`, then esbuild bundles against it. No
`package.json` in the automations dir — the file stays self-contained. Version pinning is
best-effort (latest satisfying); a follow-up could let a `// @pin pkg@1.2.3` comment lock versions.

</AccordionContent>
  </AccordionItem>
</Accordion>

## Trust &amp; the approval flow

<Alert className="my-4">
  <AlertTitle>Local automation detected → inert until the user approves</AlertTitle>
  <AlertDescription>

When the server's watcher sees a **local** automation whose id is not in the trust store (or whose
stored verdict is **rejected** but the content hash no longer matches), it marks it **pending** and
broadcasts `automationPending`. The app pops a modal stating the **title + description**, warning
that the code runs on the host on a schedule / on events, and that the user should trust the source
before installing. **Approve** loads + runs it; **Reject** keeps the file on disk and records
`rejected` in the store against the current content hash — no dialog again unless the user
re-approves from the UI _or_ edits the file, which invalidates the hash and re-prompts on the next
scan. Global automations skip this entirely.

  </AlertDescription>
</Alert>

## Open questions

<Card className="my-4">
  <CardContent className="text-sm pt-6 space-y-2">

- **Root registration timing** — before the app has _ever_ opened a project, the server can't know its `.pragma` root, so a cron can't run "cold" the very first time. Acceptable? (Global automations are unaffected — the server watches `~/.pragma` on startup.)
- **`ctx` surface** — how much host capability to expose (git, fs, exec, network). More power = more useful and more dangerous. Proposed: log + paths + a `@pragma/sdk` subset; exec/network available but called out in the approval dialog.
- **Cron ownership** — server holds the schedule (survives app close) and pokes the sidecar to run; the sidecar does **not** self-schedule. Confirm.
- ~~**Trust granularity** — trust is per automation id (path), one-time. Do we ever want to re-verify on external content change (git pull replacing the file)?~~ Resolved: rejected verdicts are keyed to the content hash at rejection time; any content change (Pragma editor, external edit, `git pull`) clears the rejection and re-prompts. Approved verdicts stay one-time per id regardless of edits.
