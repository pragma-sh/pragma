# A fully-featured `pragma-cli`

Grow `pragma-cli` from a single agent-status reporter into a control surface for Pragma:
worktrees, tabs, splits, the browser, and agents — all driven from the terminal. Plain
text by default, `--json` for scripting.

The hard constraint shapes everything below: **most of Pragma's logic lives in the GUI app,
not the server.** Persistent records (worktrees, tabs, splits) live in a SQLite DB owned by
`apps/pragma/src-tauri` (`db.rs`); browser tabs are native `tauri::Webview`s that only exist
while the window is open; `pragma-core::Core::handle_rpc` is still a stub. The CLI therefore
**brokers** commands through `pragma-server` to the running app, which executes them with its
existing Tauri commands and updates its UI live.

- **Transport — broker via `pragma-server`.** A new `Control` request kind turns the server
  into a request router. The app registers as the single **controller**; the CLI publishes

- **Two operations skip the app entirely.** Reading a terminal tab's scrollback and viewing
  agent statuses are already server-owned (`Session` scrollback + the agent registry), so the

- **Browser = drive Pragma's own webview tabs.** Thin wrapper over the existing `browser_*`
  Tauri commands. **No browser-automation crate needed** (see _Crate choices_).
- **Splits reuse the scripts schema.** The recursive `left`/`right` (horizontal) and

  the CLI's `--layout` input and the shared live-split type.
- **GUI ops error clearly when the app is closed** — no auto-launch.

## Architecture: the broker

The CLI never touches the DB or a webview directly. It speaks the existing framed protocol to
`pragma-server`, which routes a `Control` request to whichever connection registered itself as
the **controller** (the GUI app), waits for the matching `ControlResult`, and returns it.

```
                         ┌──────────────── pragma-server ────────────────┐
  pragma-cli  ──Control──►  router: pending{requestId → reply channel}    │
     ▲                   │  controller: Option<Writer>                    │
     │                   └───────┬───────────────────────▲───────────────┘
     │ RpcResponse               │ Control (forwarded)    │ ControlResult
     └───────────────────────────┘                        │
                                 ▼                         │
                        apps/pragma/src-tauri  ───────────┘
                        (registers as controller; runs the
                         matching #[tauri::command]; UI updates live)
```

The app already maintains a persistent server connection in
`apps/pragma/src-tauri/src/agent_events.rs` (a background thread that subscribes to agent
events and re-connects on drop). The controller registration + command loop is a sibling of
that bridge — same connection lifecycle, same `connect_with_spawn()` entry point.

<Accordion type="single" collapsible className="my-4">
  <AccordionItem value="round-trip">
    <AccordionTrigger>Request round-trip, step by step</AccordionTrigger>
    <AccordionContent>

1. **App boot.** The new control bridge opens a connection, reads `Hello`, and sends a
   `RegisterController` request. The server stores the connection's writer in
   `Registry.controller` and starts reading `ControlResult` frames from it.
2. **CLI invocation.** `pragma-cli tab list` builds a `Control` request: a `ControlMethod`
   (`tabsList`) plus a JSON payload, with a fresh `requestId`.
3. **Route out.** The server inserts `requestId → reply-channel` into `Registry.pending`, then
   writes the `Control` frame to the controller's writer.
4. **Execute.** The app's control loop matches `ControlMethod`, calls the existing Tauri
   command (`list_tabs`), and writes a `ControlResult` (payload or error) tagged with the same
   `requestId`.
5. **Route back.** The server's controller-reader pops `requestId` from `pending` and sends the
   result down the channel; the CLI's handler unblocks and writes an `RpcResponseFrame`.
6. **Print.** The CLI renders plain text, or the raw payload under `--json`.

If `Registry.controller` is `None`, the server fails the `Control` request immediately with a
`NotFound`-class error → the CLI prints `error: Pragma is not running. Launch the app first.`
(unless the command is one of the two direct-to-server reads below).

    </AccordionContent>

  </AccordionItem>
</Accordion>

  <TabsContent value="worktree">

`list` resolves the project from the current worktree's `project_id` and prints
`is_main`-first rows. `create` requires `--parent` (a worktree id) and `--branch`; the app's
`create_worktree` handles the git worktree + DB row + setup scripts.

```
$ pragma-cli worktree list
ID                                    BRANCH        TITLE        MAIN  HIDDEN
b1e2…                                 main          —            yes   no
2fb8…                                 cli           CLI work     no    no

$ pragma-cli worktree create --parent b1e2… --branch feature/x --title "Feature X"
created 9af0…  feature/x  → .pragma/worktrees/9af0…
```

`rename`, `hide`/`unhide`, and `delete` round out lifecycle management, each wrapping the
matching Tauri command. `delete` mirrors the UI's guardrails: `--force` to proceed on a dirty
tree, `--delete-branch` to drop the branch too — without `--force` a dirty worktree is refused
with a clear message rather than destroyed.

```
$ pragma-cli worktree rename 9af0… "Renamed"
$ pragma-cli worktree hide 9af0…
$ pragma-cli worktree delete 9af0… --delete-branch --force
```

`--json` emits the full `Worktree` array / object straight from the Tauri command.

  </TabsContent>

  <TabsContent value="tab">

`list` defaults to the current worktree; pass `--worktree <id>` (or `--all` for the whole
project). `read` is the interesting one — it's **direct to the server**: attach to the
session, collect the replayed scrollback frames, detach.

- `--lines N` — tail the last N lines (default sensible cap, e.g. 1000).
- `--offset N` — skip N lines from the chosen end.
- `--bytes N` — raw byte budget instead of lines.
- `--plain` (default) strips ANSI/OSC; `--raw` emits bytes verbatim for piping.
- `--watch` — after printing the scrollback, **stay attached** and stream new output as it
  arrives (`tail -f` style), until the session exits or you Ctrl-C. The attach already returns
  a live receiver, so this is the same code path left open.

`open --kind` maps to `create_tab` (+ `pty_spawn` for terminals); `--url` seeds a browser tab,
`--file`/`--diff-side` an editor/diff tab. `close` wraps `close_tab`; `rename` wraps
`rename_tab` to set a tab's display title (note: a live shell can later re-claim a terminal
tab's title via OSC, exactly as in the UI). `exec` runs a command in the worktree **without a
tab**, capturing stdout/stderr/exit — backed by a new `exec_in_worktree` that reuses the
`scripts.rs` headless runner so it inherits the same shell + worktree cwd.

```
$ pragma-cli tab list
TAB ID    KIND      TITLE              URL/FILE
t-3f…     terminal  zsh                —
t-9c…     browser   Pragma docs        https://…
$ pragma-cli tab read t-3f… --lines 40 --plain
$ pragma-cli tab rename t-3f… "build watch"
$ pragma-cli tab exec --worktree 2fb8… -- bun run typecheck
```

  </TabsContent>

  <TabsContent value="split">

The split layout is the **same recursive binary tree as run scripts** — promoted to a shared
`SplitNode` in `@pragma/constants`. A node is a leaf (a tab spec) or exactly one of a
horizontal (`left`/`right`) or vertical (`top`/`bottom`) split:

```jsonc
// pragma-cli split set --worktree 2fb8… --layout - <<'JSON'
{
  "left":  { "kind": "terminal" },
  "right": {
    "top":    { "kind": "terminal", "command": "bun run dev" },
    "bottom": { "kind": "browser", "url": "http://localhost:1420" }
  }
}
JSON
```

`set` validates the tree against the schema, then calls `set_split_layout`. `add-tab` is a
read-modify-write convenience: it loads the current layout and grafts a new pane on a
`--side`. `clear` collapses back to a single pane (`clear_split_layout`). Leaves are tab specs
(`kind` + optional `command`/`url`/`file`) rather than the script's bare command strings — the
one deliberate divergence from the scripts schema.

  </TabsContent>

  <TabsContent value="browser">

Wrappers over the existing and new `browser_*` Tauri commands, addressed by browser-tab id. All
are broker ops and **require the app running** (a webview is a live native surface):

```
$ pragma-cli browser navigate t-9c… https://example.com
$ pragma-cli browser back t-9c…
$ pragma-cli browser reload t-9c…
$ pragma-cli browser scroll t-9c… --to bottom
$ pragma-cli browser focus t-9c… "input[name=q]"
$ pragma-cli browser click t-9c… "button.submit"
$ pragma-cli browser screenshot t-9c… --out page.png
$ pragma-cli browser exec t-9c… "document.title"
$ pragma-cli browser exec t-9c… - < script.js
```

**Navigation** (`navigate`/`back`/`forward`/`reload`/`close`) maps to the existing `browser_*`
commands. The new **interaction** verbs are backed by new Tauri commands on the webview:

- `scroll` — scroll by `--x`/`--y` deltas or jump `--to top|bottom`.
- `focus <selector>` — move focus to the first element matching a CSS selector.
- `click <selector>` — dispatch a click on the first matching element.
- `exec <js|->` — **run arbitrary JavaScript in the page** (`-` reads the script from stdin)
  and return its JSON-serialized result. `scroll`/`focus`/`click` are thin, ergonomic shorthands
  built on the same `eval` plumbing.
- `screenshot [--out file.png]` — capture the webview surface to a PNG (writes `--out`, else a
  default path; `--json` returns the path). Uses the same `xcap` capture path Pragma already
  depends on.

**No `devtools` command** — opening devtools is not reliable to drive through the Tauri webview,
so it is intentionally omitted; use `exec` for inspection instead.

To create a browser tab use `tab open --kind browser --url …`. No external browser engine is
involved — see _Crate choices_.

  </TabsContent>

  <TabsContent value="agent">

`start` consolidates what the UI does today (read `~/.pragma/agents/<id>/config.json`, create a
terminal tab, `pty_spawn` the start command with the model arg, send the prompt prefill) into
one new `start_agent` Tauri command shared by the UI and the CLI. It returns the agent's tab id.

`status` is **direct to the server**: open a `SubscribeAgents` subscription, take the snapshot,
print one row per agent with its `tabId`, then disconnect. With `--watch` it keeps the
subscription open and prints each delta as agents change state — a live dashboard for scripting
or a status line.

```
$ pragma-cli agent start --worktree 2fb8… --agent claude-code \
    --model claude-opus-4-8 --prompt "Fix the failing test"
started claude-code in 2fb8…  tab=t-7a…

$ pragma-cli agent status
WORKTREE  AGENT        STATUS      TAB
2fb8…     claude-code  running     t-7a…
b1e2…     opencode     attention   t-1d…
```

`report` is the existing status-reporting verb, now nested under `agent` as `agent report` with
`--agent` a flag on the subcommand. It is **direct to the server** (writes an `AgentReport`) and
its reporting logic is unchanged — only the command path moved. The old top-level
`pragma-cli --agent <id> report …` is removed; the opencode / Claude Code / Cursor plugins are
updated to the new form and reinstalled (see _Phase 4_).

```
$ pragma-cli agent report --agent claude-code started
```

  </TabsContent>
</Tabs>

## Output: plain vs `--json`

<Card className="my-4">
  <CardContent className="text-sm space-y-2 pt-6">

- **Default = plain text.** Lists render as aligned columns; single-object commands print a
  short human line. Errors go to stderr, data to stdout, so piping stays clean.
- **`--json` = structured.** Each command serializes its result type (the Tauri command's
  return shape, or a small CLI-owned struct for direct reads) with `serde_json`. One object or
  array per invocation — no log noise on stdout.
- **Exit codes:** `0` success, `1` operation error, `2` usage error (clap), distinct from the
  app-not-running case so scripts can branch.

</CardContent>
</Card>

## Risks & edge cases

<Accordion type="multiple" className="my-4">
  <AccordionItem value="r1">
    <AccordionTrigger>Single controller, reconnection, and dropped replies</AccordionTrigger>
    <AccordionContent>

Exactly one controller (the app). On reconnect (app restart) the new connection replaces the
old controller writer. Any `pending` requests whose controller dropped must be failed with a
clear error rather than hanging — every `Control` gets a **timeout** (e.g. a few seconds) so a
crashed app can never wedge the CLI. Multiple app windows: only the main window's bridge
registers.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="r2">
    <AccordionTrigger>`tab read` is bytes/frames, not lines</AccordionTrigger>
    <AccordionContent>

The server's scrollback is a frame buffer of raw output, capped at `SCROLLBACK_LIMIT` — it is
**not** the full terminal history and not line-addressed. The CLI assembles the bytes, then
splits/strips for `--lines`/`--plain`. Document that `read` returns "as much as the server still
holds," and that `--bytes`/`--lines` are best-effort over that window.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="r3">
    <AccordionTrigger>Worktree/tab references are UUIDs</AccordionTrigger>
    <AccordionContent>

IDs are UUIDs — unfriendly to type. Mitigations: `--worktree` defaults to the current env id;
accept a unique branch-name prefix as an alias in a follow-up; always print full ids in `list`
so they can be copied. Keep the first cut id-only to avoid ambiguity bugs.

    </AccordionContent>

  </AccordionItem>
  <AccordionItem value="r4">
    <AccordionTrigger>Split add-tab races the UI</AccordionTrigger>
    <AccordionContent>

`add-tab` is read-modify-write on a layout the UI may also be editing. Route the mutation
through the app (which owns the in-memory layout) rather than the DB so it serializes against
live edits; the existing `set_split_layout` already persists frontend-owned JSON, so the app
applies then persists in one step.

    </AccordionContent>

  </AccordionItem>
</Accordion>
